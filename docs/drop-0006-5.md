# DROP 0006.5 — Local fracture indexing and scalable damage ownership

One sentence: a local impact should cost what its neighbourhood holds, not what
the world's whole damage history contains.

This drop changes no destruction behaviour. The integrated demolition results,
the historical eight-case destruction pack and the interaction benchmark all
reproduce bit-for-bit; the only thing that moves is how much work a capture
does to reach the records it was always going to read.

## What it used to do

`FractureState` held two flat maps — `BTreeMap<DamageSite, CellFracture>` and
`BTreeMap<BondSite, BondFracture>` — keyed by `(space, cell)` and `(space,
bond)`. Within `DamageSpace::StaticWorld` that orders records by cell address,
which is not spatially local: the records for one 16³ volume are scattered
through the ordering rather than contiguous in it.

Three consequences, in descending order of how much they mattered:

* **`snapshot_space` copied the whole space.** `FractureJobInput::capture`
  bounds its world copy to at most 27 known regions, byte- and volume-budgeted,
  and then called `state.snapshot_space(space, limits.damage_records)` — which
  walked and copied *every static record in the world*. A hit on one wall paid
  for the damage history of every other wall. Worse, `damage_records` could
  refuse a capture outright because of cracks nowhere near the impact, which
  turns unrelated history into a denial of service against local destruction.
* **`region_fracture` scanned everything per region.** `self.cells.values()
  .filter(owns_cell)` — a full pass to find one region's records, run once per
  region by the save and eviction paths.
* **`static_regions` scanned everything** to answer "which regions hold
  damage", which is the first question a streaming host asks.

`forget_cell` was already local — a cell record plus its six face bonds, seven
map operations — and is unchanged.

## What it does now

The two maps and a region index over them live in one private type,
`RegionIndexed<K, V>`. The map is private to that type, so every insertion and
removal maintains the index by construction: there is no code path that can
update one and not the other. A `StaticSite` trait gives each key the regions it
touches.

Queries added or rewritten:

* `snapshot_regions(space, regions, max)` — collects only records the given
  regions can reach. `capture` now calls this with the same `known_regions` it
  already bounds its world copy by.
* `region_fracture(region)` — index-narrowed, then filtered by the unchanged
  ownership rule, yielding the same records in the same canonical order.
* `static_regions()` — a walk of the index's keys.
* `records_in_regions(regions)` — counts without copying, for measurement.

Fragment-local records are deliberately **not** region-indexed. They are owned
by an exact `FragmentId` and already sit contiguously under their space in the
authoritative map, so `cells_in`/`bonds_in` already answer in time proportional
to that one fragment. Indexing them would add bookkeeping and buy nothing.

### Two spatial questions, deliberately answered differently

This is the subtle part, and getting it wrong in either direction is a bug.

* **Persistence asks who saves a record.** The answer must be exactly one
  region, or an extract/restore cycle duplicates or drops it. That rule is
  unchanged: a cell belongs to its cell's region, a bond to its **lower** cell's
  region, as `owns_cell`/`owns_bond` always said.
* **Analysis asks who can read a record.** A bond across a region seam is
  readable from both sides. A capture that saw only the owning side would hand
  the worker an intact bond where there is a crack.

So the index stores a bond under *every* region it touches — one entry, or two
when it straddles — and the persistence paths filter that down to sole
ownership. `a_boundary_bond_is_readable_from_both_regions_but_owned_by_one` and
`a_boundary_bond_survives_one_sides_eviction_without_duplicating` pin both
halves.

### Why the index is not an authority

It answers one question — "which records could lie in these regions" — and the
answer is only ever used to narrow a candidate set that is then read from the
authoritative map. Nothing consults it to decide topology:

* exact occupancy connectivity remains the permanent topological oracle;
* the fracture-aware classifier remains the crack-cut classifier beside it;
* detachment still requires a settled, current, complete result and atomic
  admission.

Deleting the index and scanning instead would be slower and would change no
result. That is the property `an_index_rebuilt_from_the_records_matches_the_
maintained_one` pins: it rebuilds the index from the records alone after
insertions, straddling insertions, removals, repeated removals and draining, and
asserts equality each time. If the maintained index could ever disagree with
what the records imply, that test fails.

Determinism is unaffected by construction: `snapshot_regions` collects into
`BTreeMap`s, so canonical output does not depend on the order regions were
visited. The region walk is still ordered, so that the *budget* trips
deterministically rather than depending on a caller's set iteration.

## Benchmark methodology

`cargo run --release -p engine_stress --bin fracture_locality_bench`. The same
demolition-building impact — radial blast, radius 6, 16,000 energy, coherent
model, 27 known regions — is run against fracture states carrying increasing
unrelated history, 5 samples per rung, median reported.

Two things make the benchmark bite in both directions:

* Identical **local** history at every rung: 64 cell records and 64 bond records
  on real roof cells inside the known regions. Without this the local record
  count is zero and an implementation that collected *nothing* would pass the
  constancy check while proving nothing. The benchmark asserts
  `snapshot_records > 0` and `snapshot_records == local cells + local bonds`.
* Unrelated history spread over many distant regions, written through
  `restore_region` — the ordinary streaming load path, not a test-only back
  door.

The comparison is of local state. The whole-state digest legitimately differs
between rungs because the unrelated history is part of it, so the benchmark
hashes the records the impact's own regions own, and compares that.

Timings are reported, never asserted on: this ran in a shared cloud container
with no GPU, and a wall clock there is not a pass criterion.

## Measured results

Identical at every rung, asserted by the benchmark itself:

| quantity | value |
|---|---|
| failed cells | 54 |
| broken bonds | 168 |
| fragments created | 12 |
| evaluated work | 887 |
| structural checksum | `3b07fb1588d23136` |
| local fracture checksum | `77e017301e150e6a` |
| snapshot records | 128 |

Scaling, median of 5 samples:

| unrelated records | total in state | snapshot records | index regions | capture | worker | commit |
|---|---|---|---|---|---|---|
| 0 | 128 | 128 | 1 | 0.0389 ms | 3.4896 ms | 0.1643 ms |
| 10,000 | 10,128 | 128 | 21 | 0.0474 ms | 3.4395 ms | 0.1727 ms |
| 100,000 | 100,128 | 128 | 51 | 0.0647 ms | 3.9794 ms | 0.1909 ms |
| 1,000,000 | 1,000,128 | 128 | 101 | 0.0863 ms | 3.8392 ms | 0.1881 ms |

The headline: **7,813x more damage history in the state costs 2.2x more capture
time**, and the snapshot is provably the same 128 records throughout. Before this
drop the snapshot at the last rung would have been 1,000,128 records — and with
the default `damage_records` ceiling of 32,768 it would not have been a snapshot
at all, it would have been `JobRefusal::SnapshotBudget`.

The residual 2.2x is not record copying, because the record count is constant.
It tracks `index_regions`: 27 region lookups into a map of 101 keys rather than
1, plus the general memory pressure of a structure holding a million entries.
That is a design claim about where the remaining time goes, not a measurement of
it — the benchmark does not attribute the residual.

## Memory overhead

Measured sizes: a cell record is 48 bytes, a bond record 48 bytes, and an index
key 40 bytes for both maps. The index stores one entry per static cell record
and one or two per static bond record, so at the million-record rung its keys
alone are **38.15 MiB against 45.78 MiB of records — about 83% overhead on the
record payload**, before the B-tree node overhead on either side.

That is the honest price of this design and it is not small. It is paid because
the index duplicates each record's full 40-byte key. Two cheaper shapes exist
and neither was taken here: storing volume-local offsets instead of whole
`CellPos` values, or ordering the authoritative keys volume-major and dropping
the second structure entirely. The second is the more attractive and was
rejected deliberately — `FractureState::digest` iterates the maps in key order,
so reordering them would move every committed fracture checksum, and this drop's
first requirement was that no existing result move. Revisiting it is future
work, and it would want the digest canonicalised independently of storage order
first.

## Known limitations

* **`prune_against` still scans the whole state.** It is the belt-and-braces
  sweep for a bulk change whose extent the host did not track — a repaint, a
  region swap, a world reload — and its own documentation has always said its
  cost is the whole state. It also reports `records_examined`, which
  `fracture_ownership.rs` asserts exactly, so narrowing it would change
  observable behaviour. Left alone on purpose; a host that knows what it changed
  should call `forget_removed` instead, which is already local.
* **`forget_space(StaticWorld)` is still whole-space**, by definition. For
  `FragmentLocal` it is bounded by that fragment, which is the case that occurs.
* **Region granularity, not volume.** Every consumer — `capture`'s known set,
  `region_fracture`, `take_static_region`, `static_regions` — is region-keyed, so
  a volume-level index would add entries without a caller to serve. If a future
  impact path wants a tighter bound than a region, this is where it changes.
* **The 2.2x residual is unattributed.** It is small in absolute terms (under
  0.1 ms) but it is not zero, and the benchmark measures it without explaining
  it.
* **The index is not residency.** A region absent from `static_regions` holds no
  records, which is not the same as being known to be undamaged. A host must
  still load a region before concluding anything about it;
  `an_unlisted_region_is_unknown_rather_than_undamaged` records that distinction
  so nobody later reads the index as a residency oracle.
