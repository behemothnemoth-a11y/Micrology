# DROP 0001 — World Kernel: status

**Goal.** Prove the engine owns, displays, edits, saves and reloads its own
volumetric geometry efficiently, without Minecraft.

## Deliverables

Against the eleven numbered items in `vision/03_DROP_0001_SCOPE.md`:

| # | deliverable | state |
|---|-------------|-------|
| 1 | open a native window | implemented, observed |
| 2 | move a free camera through a scene | implemented, not driven by hand |
| 3 | create/load a small engine-native world | implemented, tested |
| 4 | store cells and materials independently of Minecraft | implemented, tested |
| 5 | compile visible surfaces into renderable geometry | implemented, tested |
| 6 | avoid drawing internal faces | implemented, tested |
| 7 | render the result | implemented, observed |
| 8 | edit a small local region at runtime | implemented, engine side tested |

Both optional stretch items are in: greedy merging of coplanar same-material faces,
and cross-chunk hidden-face removal. The exact extractor was built first behind the
`SurfaceCompiler` trait and is kept permanently as the oracle, as the scope asks.

## How this was verified

DROP 0001 was built in a headless cloud container, so the sandbox was run under
Xvfb against Mesa's `lavapipe` software Vulkan driver. That is slow, but it
exercises the real path: real winit window, real wgpu/Vulkan device, real meshes
uploaded and drawn.

What was observed directly:

- The window opens, the scene renders, and the HUD reports live numbers.
  `docs/images/sandbox.png` is a real frame from that run, not a mock-up.
- Pressing `F5` wrote `saves/sandbox.world.json`, confirming keyboard input
  reaches the engine and the save path works in the app and not only in tests.
- That file contained exactly the 32,105 occupied cells the HUD reported, reloaded
  through `engine_io` with identical stats, and re-serialized byte-identically —
  so canonical output holds on real app data, not just on test fixtures.
- Rendering the same scene with `ExactCompiler` instead of `GreedyCompiler`
  produced a pixel-identical frame, which is the oracle doing its job at the
  rendering level rather than only in tests.

### Two bugs the first run caught that the tests could not

**Vertex colours were sRGB where linear was required.** Every surface rendered
pale and washed out. `MeshData` documented its colours as linear but was handed
raw sRGB components. Fixed by adding `Rgb::to_linear_f32` with the proper sRGB
transfer function, now used by the mesh builder and covered by a unit test. No
geometry test could have caught this — the quads were always correct.

**The initial camera pose framed the brick room, not the scene.** Cosmetic, but
it is the first thing anyone sees. Pulled back.

### What is still not verified

- **Mouse-look, carving, placing, painting and `G` were not exercised at
  runtime.** Keyboard input was, via a synthetic `F5`. Driving a grabbed-cursor
  free camera headlessly was not attempted, so the camera and edit systems are
  verified as "compiles, and its engine-side effects are tested", not as "feels
  right in the hand". Expect to tune mouse sensitivity and fly speed on first
  real use.
- **No real GPU has run this.** `lavapipe` is a software rasteriser, so the frame
  rate in that screenshot (12 fps at 1280x720) says nothing about performance and
  should not be quoted as a benchmark.
- **Shadow quality is unconfirmed on real hardware.** The bias values are a mild
  nudge above Bevy's defaults, chosen without a confirmed acne problem to solve.

## Measurements

Design principle 8 asks for numbers, so here are real ones from the test suite
rather than estimates. A solid 16³ chunk standing alone:

| | exact | greedy |
|---|---|---|
| exposed unit faces | 1536 | 1536 |
| quads emitted | 1536 | **6** |
| vertices | 6144 | 24 |
| triangles | 3072 | 12 |

Two solid chunks side by side lose all 512 faces at their shared seam — 256 from
each side — and each compiles to 5 quads rather than 6.

On a slab-plus-blob scene closer to real terrain, greedy meshing cuts the quad
count by more than 10x; `merging_actually_merges_on_realistic_terrain` asserts that
bound so a regression in merging shows up as a test failure, not as a silent
slowdown.

From the demo scene in the screenshot, as the HUD reported it: 18 chunks, 32,105
occupied cells, 12,064 exposed unit faces compiled into 1,532 quads — a 7.9x
reduction — for 6,128 vertices and 3,064 triangles. A full 18-chunk rebuild took
about 20 ms on a software rasteriser; a single-chunk edit rebuild is one chunk of
that work.

What these numbers are **not**: a frame-rate claim. Nothing here has run on a real
GPU, and the principle against claiming FPS improvements from geometry counts
applies to this table too.

## Known limitations

Deliberate, scoped-out, or simply not done yet:

- A chunk is exactly one 16³ volume. Decoupling chunk size from volume size is
  phase B.
- No streaming, no LOD, no regions above chunks. Everything loaded is in memory and
  in one save file.
- Vertices are not shared between quads. Four per quad, no index reuse across
  quads, because neighbouring faces usually differ in normal or material.
- No frustum or occlusion culling beyond what Bevy does per entity, and no
  asynchronous mesh compilation — rebuilds happen inline on the main schedule.
- No transforms on volume data (rotation, mirroring), which `astra-microblocks`
  had. Needed before sculptures and reusable prefabs.
- No collision representation beyond the cell data itself, which the raycast reads
  directly.
- The save format has no world metadata: no seed, no name, no spawn point.
- `raycast` lives in the sandbox and has no tests. It is the only real algorithm
  outside the engine crates, which is the wrong place for it.
- Palette interning is a linear scan. Fine for the handful of materials a volume
  really holds; it would want a reverse map if palettes ever got large.

## Next smallest step

**Run the sandbox on a machine with a real GPU and a mouse, and spend ten minutes
carving.** Rendering and saving are confirmed; the interactive half is not.
Expect to adjust mouse sensitivity, fly speed and reach, and to find out whether
editing at a chunk seam looks seamless in motion rather than merely in a test.

Immediately after, in order:

1. Move `raycast` out of `apps/sandbox` into `engine_world` (or a small
   `engine_pick`) with real tests — axis-aligned rays, diagonal rays, rays
   starting inside solid material, rays that miss, and rays crossing chunk seams.
   It is the only real algorithm outside the engine crates and the only one with
   no coverage.
2. Open DROP 0002 (see `drop-0002-scope.md`): scale, regions, streaming and
   asynchronous meshing.

Volume transforms (rotate, mirror) were previously listed here as step 2. They
have been moved to the import/export drop, where something actually consumes
them: they operate on volume data, and DROP 0002 reshapes exactly that by
decoupling the storage leaf from the residency and render units. Written now,
they would be rewritten.
