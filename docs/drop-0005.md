# DROP 0005 — Material Mechanics and Structural Capacity

Status: **in progress**

Scope: docs/drop-0005-scope.md

DROP 0005 is the first drop in which two cells made of different materials
behave differently. DROP 0004 deliberately kept mechanics uniform so that the
event, accumulation, detachment and fragment pipeline could be proved without a
mechanical model confusing the question. This drop pays that debt in three
ordered steps: give materials mechanical identity, make the existing damage path
material-aware without redesigning it, then add a deterministic, bounded,
optional model of structural capacity.

This remains an engine milestone. Mechanical realism is never mandatory. A
floating island, impossible castle or magical bridge stays valid authored data
and must not need a fake infinite-strength material to hold itself up.

---

## 0005.0 — mechanics architecture and participation contract

**Status: complete**

Adds the `engine_mechanics` crate containing vocabulary only. There is no
capacity model, no load path and no failure in it yet, which is the point: the
contract that keeps mechanics optional has to exist and be tested before
anything can depend on it.

The crate sits downstream of `engine_destruction`:

```text
engine_core ──┬── engine_volume ──── engine_world ──┬── engine_destruction ──┬── engine_mechanics
              └── engine_geometry ──────────────────┘                        └── engine_io
```

That placement is what will make the rest of the drop additive. `DamagePolicy`
and `DamageFailurePolicy` are traits defined upstream, so material-aware damage
in 0005.2 is a matter of writing new implementations here rather than modifying
the DROP 0004.6 contract. Nothing in this pass changed any existing crate; the
only edits outside the new directory were registering it in the workspace.

**Mechanical data does not extend `Material`.** `MechanicalRegistry` is a side
table keyed by `MaterialId`, and being empty is a valid, expected, permanently
supported state. `engine_core` stays dependency-light and free of capacity
vocabulary that meshing, streaming and I/O have no use for, and strength stays
out of material identity — which matters because making strength a `Material`
property is one short step from making support one, and that is forbidden.
A material with no profile has **no mechanical identity**, which callers must
not confuse with having a defaulted one.

**Every mechanical quantity is an integer.** `Milli` is a signed fixed-point
scalar in thousandths with saturating arithmetic throughout, and the fixed-point
multiply widens through `i128` so two large quantities cannot wrap before
rescaling. There is no `From<f64>`, deliberately: a conversion that existed
would eventually be used on a hot path. Determinism in the later solver is
bought here, by never introducing the problem.

**Participation is per system, not one global switch.** Seven separable systems
— gravity, anchoring, connectivity detachment, applied damage, fragment physics,
material mechanics, structural capacity — each resolve independently across four
scopes: engine, world, object, gameplay. Most specific wins. Participation is a
**tri-state**, because two states would leave a more specific scope unable to
turn off what a broader one enabled, and that is precisely the case a fantasy
region most needs.

The engine default is that **nothing participates**. A world that never mentions
policy gets no physical behaviour from this crate at all, which is exactly what
every pre-DROP-0005 world already does.

Persistence is a sidecar document, so no existing format changed. Unknown
physical systems and unknown policy scopes are ignored on load rather than
rejected, matching how the cell format already tolerates unknown keys: a world
written by a later build still loads here.

Acceptance passed:

- **19 / 19** focused tests (6 fixed-point, 13 policy/registry/persistence);
- most-specific-wins verified across **every ordered pair** of the four scopes;
- a specific scope can disable what a broader one enabled, and a gameplay
  override beats all three scopes below it;
- an absent profile reads as absent, never as defaulted;
- settings round-trip through JSON with a stable serialized form;
- unknown systems and scopes load without error and without being mistaken for
  a more specific scope;
- full engine regression **537 passed / 0 failed** — the DROP 0004 baseline of
  518 plus exactly the 19 new tests, with nothing else moved;
- DROP 0004 chaos **14 / 14** and DROP 0003 chaos **9 / 9** still green, and
  `chaos4`'s committed report is byte-identical;
- Clippy with warnings denied across `engine_mechanics`, `engine_destruction`,
  `engine_stress` and the sandbox; formatter clean.

No capacity, no failure, no solver. Those begin at 0005.4.

## 0005.1 — mechanical material profiles

**Status: complete**

The inert data: density, tensile, compressive and shear capacity, toughness and
a failure character. Every field defaults to zero, so a profile written by an
older build loads without values being invented for it, and a profile whose
capacities are all zero is a material that carries nothing — a legitimate
authored state for decoration, and not the same as having no profile at all.

The reference set covering wood, masonry, concrete, steel and glass ships bound
to caller-chosen `MaterialId`s as **example data, never engine truth**. The
numbers are plausible real-world magnitudes chosen so the relationships are
recognisable: masonry is an order of magnitude weaker in tension than in
compression, glass out-carries concrete while being far less able to take a hit,
and steel is both the strongest and by far the heaviest.

Acceptance passed: **12 / 12** focused tests, including that an absent profile
stays absent, that insertion order never leaks into iteration order, and that a
0005.0-era profile carrying only an id loads as inert rather than as steel.

## 0005.2 — material-aware damage policies

**Status: complete**

`MaterialDamagePolicy` and `MaterialFailurePolicy` are new implementations of
the upstream `DamagePolicy` and `DamageFailurePolicy` traits. This is the payoff
of placing the crate downstream of `engine_destruction`: the 0004.6 contract,
the 0004.7 sparse accumulator and everything built on them are untouched.

Toughness is used exactly once. It sets the **threshold** — how much accumulated
damage breaks a cell — and nothing else uses it. **Delivery** is modulated
separately by failure character: brittle material transmits more of a hit than
it should and shatters, ductile material absorbs part of it. Those are different
properties, so the two are not double-counting the same one.

The result is the behaviour the drop exists for: one light tap shatters glass,
and sixty of the same taps leave steel standing. Across a mixed wall of
alternating glass and steel, a single event fails every glass cell and leaves
every steel cell merely scratched, repeatably.

Acceptance passed: **7 / 7** focused tests. An unprofiled material and an empty
registry each reproduce the uniform reference byte-for-byte, through the real
evaluation and accumulation path rather than a mock.

## 0005.3 — density-aware fragment mass and inertia

**Status: complete**

Mass now aggregates from material density, and `reference_detachment_impulse`
stays exactly where it is as the material-neutral reference. Aggregation is
integer and order-independent, so a fragment's mass does not depend on traversal
order.

A cell of unprofiled material contributes one whole unit, which is precisely the
DROP 0004 cell-count approximation — so an empty registry reproduces the old
impulse exactly, asserted directly against the reference function. Zero-density
material clamps rather than dividing by zero, keeping a decorative material inert
instead of explosive.

Identical geometry in wood and in steel now receives measurably different motion
from the same impulse; DROP 0004 could not tell them apart at all.

Acceptance passed: **7 / 7** focused tests.

## 0005.4 — exact load representation, without failure

**Status: complete, with a finding that changes 0005.7**

The integer capacity network is built and solved. Nothing acts on it: this pass
computes an answer and returns it, and cannot fail a cell or move anything.

Each participating cell owes its weight to an anchor; each face carries only so
much, chosen from the weaker of the two materials and the load mode across it.
Load mode is pure geometry — downward is compression, upward is tension,
sideways is shear — which is why no direction had to be threaded through
`DamageEvent` or `DamageWork`. Satisfaction is a feasible integer flow; the
minimum cut names the connections that are the bottleneck.

Two behaviours are worth recording because the tests found them rather than the
design anticipating them. A cell's own load edge is **excluded** from the
reported cut: such an edge is in the mathematical minimum cut precisely when
that cell's weight is carried *in full*, so reporting it would name every
healthy cell as a failure. And an **empty** cut with demand unmet means
something quite different from a weak joint — no load path to any anchor exists
at all. That is an unsupported structure rather than an under-strength one, and
it is connectivity's question, not this module's.

Conservative everywhere, as required: reaching a non-resident region yields
`Indeterminate` with the regions needed; spending either the memory or the work
budget yields `Deferred`. Neither is a conclusion, and `is_conclusive()` says so.
A cell whose material has no profile is left out of the network entirely, so a
world with an empty registry builds an empty network, owes nothing and is
trivially satisfied — exactly how a pre-DROP-0005 world should behave.

Acceptance passed: **12 / 12** focused tests, including identical repeated
solves and an answer independent of which root the caller supplied.

### The finding

Decision C chose the exact per-cell network and said the coarsened fallback
would be decided on measured evidence. The measurement is in
`docs/diagnostics/drop0005_4_capacity/` and it is decisive: 2,304 cells solve in
122 ms, and 5,184 cells — 2.25× the geometry — take **1.31 s**. The solve is
roughly quadratic in cells, and a 24×24×8 block is a small building, not a
landscape.

So the fallback is now chosen. **A coarsened network is required, not
optional**, and 0005.7 is load-bearing rather than the optional experiment it
was scoped as. The exact solver stays precisely as it is, as the oracle — it is
simple enough to be obviously correct, which is the property worth keeping, and
the engine already works this way with `ExactCompiler`. The integer formulation
does not change.

The bounds are why this is a finding and not a hazard: a host that sets
`CapacityLimits` gets `Deferred` rather than a stall, and `Deferred` can never
fail a cell.

## 0005.5 — structural capacity evaluation

**Status: complete**

Turns the solve into an answer a host can ask for, gated by participation.
`CapacityVerdict` is `Sufficient`, `Insufficient` with the connections to blame,
`Inconclusive`, or `NotEvaluated` — and that last one is deliberately distinct
from `Sufficient`. "Nobody asked" and "it holds" are different facts, and
collapsing them would quietly make mechanics feel mandatory. A disabled policy
returns before a network is built, so disabled mechanics costs nothing rather
than merely deciding nothing.

### The one-cell support cliff, answered

DROP 0003 recorded that a component attached by a single cell is *supported*,
correct for binary topology and inadequate for anything load-bearing. That
answer has not changed and must not: connectivity remains the topological oracle
and still says "attached", which the acceptance asserts directly by running
`classify_component` before and after the capacity question and requiring
`Supported` both times.

What changed is that a second, separate question can be asked of the same
geometry. A two-by-two steel tower on a **one-cell** masonry neck is connected
and overloaded, and the verdict names the neck. The identical tower on a
**two-by-two** neck stands, because four masonry joints carry what one could
not. Connectivity cannot tell those two structures apart. Mechanics can.

The bottleneck is reported as the neck's lower face rather than its upper one.
Both faces are masonry-governed and so identical in capacity, which makes either
a valid minimum cut; the acceptance asserts that the named connection passes
through the neck and is compressive, rather than over-specifying which face.

Three separations hold, and the tests pin each: an *unsupported* structure
(nothing reaches an anchor, no joint to blame) stays distinct from a *weak* one;
an inconclusive verdict blames nothing, so nothing could be acted on; and an
object-scope override can disable what the world enabled while a gameplay
override turns it back on.

Acceptance passed: **8 / 8** focused tests.

## 0005.7 — conservative capacity witness

**Status: complete** (taken before 0005.6, see below)

The 0005.4 measurement made this pass load-bearing rather than optional, and
made its ordering wrong. A live collapse path cannot call a 1.3-second solver
every step, so the accelerated path was built before the pass that would depend
on it.

The witness does not estimate. Proving a flow network *insufficient* means
reasoning about every cut; proving it *sufficient* needs only one feasible flow,
exhibited. So the sweep tries to construct an actual routing of every cell's
weight down to an anchor in one descending pass, and `DefinitelySufficient` means
that routing exists and was built — a certificate, which guarantees the exact
solver agrees.

It obeys the `support_witness` contract exactly: `DefinitelySufficient` or
`NeedExact`, never a declaration of failure. It is written independently of
`capacity.rs` — a downward accumulation sweep sharing no code with the flow
solver — because an oracle that shares code with the thing it validates is not
an oracle.

**352× on the largest case.** 5,184 cells drop from 1.41 s to 4.0 ms, and the
saving grows with size because the witness is linear where the exact solver is
quadratic. It proved every sound structure in the measurement set and deferred
only on the two the exact solver rejects, which is the right division of labour:
the expensive path runs when something is genuinely suspicious rather than on
every healthy building.

Its incompleteness is deliberate and tested as such. A cantilever is sound and
the witness cannot see it — the sweep only pushes downward, finds nothing beneath
the overhanging cell, and declines; the exact solver routes that weight sideways
and down. Being bad at finding routes costs a fallback. Being wrong about one
would cost a building.

Acceptance passed: **7 / 7** focused tests, including the two that matter most —
the witness never contradicts the exact solver across the scenario matrix, and no
input can make it return anything readable as overloaded.

## 0005.6 — progressive mechanical failure

**Status: complete**

The first pass in this drop that changes what the world does, and it adds no
machinery for doing it. An overloaded connection produces a failed cell; that
cell goes through `static_failure_batch`, the existing `WorldEditBatch` path,
connectivity and detachment exactly as a cell failed by applied damage already
does. There is no mechanical fragment system and no second detachment
mechanism, because a second way to destroy something is a second thing to keep
correct.

The cheap path runs first: a structure the witness can prove sound costs one
linear sweep and never builds a flow network. Only a structure the witness
declines reaches the exact solver.

Bounded three ways, independently — generation depth, failures admitted per
step, and the capacity budgets underneath — reusing the discipline 0004.8
established for secondary damage. Every budget holds rather than collapsing:
a spent capacity budget yields `Held(Inconclusive)` and destroys nothing.

**Mechanics declines the unsupported case on purpose.** A structure reaching no
anchor at all is unsupported rather than under-strength, and detaching it has
been connectivity's job since DROP 0003. Mechanics may only add a failure reason
to geometry that is genuinely attached.

### Two rules the tests found

The first implementation broke its own foundation. Masonry on masonry ties on
capacity, and the first tie-break written was canonical cell order — which
chose the lower cell, so the anchored footing failed and a local joint failure
became a wholly unsupported structure. Two rules now hold, each with a
regression test:

- **An anchored cell never fails.** An anchor is the author's statement that
  something is held up. Mechanics may break what rests on a foundation; it may
  not erase the foundation.
- **A capacity tie sheds the load, not the support.** The side pushing load into
  the joint is the one that gives way, so collapse propagates downward from
  above the way a real one does.

With those in place the overloaded wall sheds its lowest course, the footing
survives intact and still anchored, and the remainder — now attached to nothing
— is left for connectivity to turn into falling debris. That division is the
whole design: mechanics breaks the joint, the existing pipeline handles
everything after it.

Acceptance passed: **11 / 11** focused tests, including identical collapse
across repeated runs, the generation ceiling holding at exactly one generation
when set to one, and the same wall standing untouched forever with mechanics
disabled or overridden off at object scope.

## 0005.8 — participation and fantasy acceptance

**Status: complete**

The final participation matrix is now exercised against the current post-DROP-0006
engine rather than only against the earlier individual unit tests.

Six focused acceptance cases prove:

- full mechanics enables material-aware damage, connectivity detachment and
  structural capacity independently;
- damage-only remains valid with material mechanics, connectivity and capacity
  disabled;
- connectivity-only identifies a floating island without running damage or
  capacity;
- a silent policy leaves an overloaded world of profiled masonry completely
  inert;
- a world may enable every system while a more-specific fantasy object disables
  gravity, connectivity detachment, fragment physics and structural capacity,
  yet still accepts local material-aware damage without moving/collapsing;
- neighboring residency regions can use different participation policy while
  using the exact same masonry material/profile — no fake infinite-strength
  material is involved.

The new matrix is in `tests/participation_fantasy.rs`: 6 passed, 0 failed in
GitHub Actions run 202. No production code change was required.

See [drop-0005-8.md](drop-0005-8.md) for the complete matrix and boundary.
