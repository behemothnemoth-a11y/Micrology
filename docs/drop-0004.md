# DROP 0004 — Destruction at Scale + Applied Damage

Status: **in progress**

Scope: docs/drop-0004-scope.md

DROP 0004 starts from the completed DROP 0003 destruction foundation and moves
in a strict order: first make destruction obey the same bounded-world rules as
static terrain, then build force/damage/progressive destruction on top of that
foundation.

This remains an engine milestone, not a game milestone. Physically impossible
authored worlds are valid. Gravity, connectivity destruction, damage, fragment
physics, material mechanics and later structural stress remain separable systems
that a game can choose to use or not use.

---

## 0004.0 — scope and acceptance contract

**Status: complete**

Locked the milestone around two ordered goals:

1. destruction-scale infrastructure;
2. applied force/damage mechanics.

Material-specific stress remains a later layer. DROP 0004 may prove damage with
a uniform/default mechanical response, but it does not make steel, wood, glass
or concrete behave differently yet.

The fantasy-world invariant is explicit:

> No core physical system is required for authored world validity.

A floating island does not need to pretend to be infinitely strong steel. A game
may supply a suspension/support rule, disable structural stress, enable local
damage, keep fragment physics, or choose another combination.

### Acceptance matrix established

The scope now requires deterministic coverage for:

- long travel through worlds containing persisted fragments;
- large off-camera fragment populations;
- destruction at streaming boundaries;
- repeated and radial damage;
- fragment re-fracture;
- bounded secondary damage;
- stale async work;
- deterministic replay;
- an intentionally unsupported/fantasy structure with physical participation
  disabled.

## 0004.1 — fragment spatial residency

**Status: complete**

DROP 0003 persisted fragments and indexed them spatially, but the sandbox still
loaded the complete fragment store at startup. That made fragment count a hidden
whole-world memory cost.

0004.1 separates four lifetimes that had been easy to conflate:

1. persisted existence — the fragment exists in the world;
2. storage residency — its native volumetric payload is in RAM;
3. render residency — it currently owns render-derived data/entities;
4. physics residency — it currently owns a backend rigid body/collider.

Render and physics residency already had independent radii. This pass adds the
missing storage-residency layer.

### Engine residency state machine

engine_destruction::FragmentResidency now owns deterministic fragment payload
residency policy.

It tracks wanted fragment ids, bounded active loads/saves, per-fragment load
generations, and the revision known clean on disk.

It emits three actions: Load, Save, and Drop.

Important invariants:

- a fragment named by several overlapping regions is loaded once;
- a dirty fragment must save before it may drop from RAM;
- an async load that finishes after the fragment stopped being wanted is
  discarded rather than resurrected;
- a save writes one exact fragment revision;
- if the fragment moves/changes while its save is in flight, the returned save
  does not mark the newer revision clean;
- clean storage eviction does not delete the persisted fragment.

Tests pin each of those cases.

### Unloaded is not deleted

The DROP 0003 index writer could safely derive the complete index from the
in-memory FragmentStore, because DROP 0003 loaded that complete store.

That becomes destructive under streaming: rebuilding an index from a partial
resident store would silently erase every valid off-camera fragment.

engine_io::FragmentIndex is now an independently maintainable authoritative
discovery structure with operations to construct from a complete store, upsert
one authoritative fragment, explicitly delete one fragment identity, advance
destruction-sequence state without moving backwards, and serialize/save the
authoritative index without requiring all payloads in RAM.

The distinction is hard:

> Storage eviction never removes a fragment from discovery. Only an explicit
> authoritative deletion may do that.

Engine tests preserve this invariant.

### Live index vs persisted index

The sandbox keeps two index states on purpose.

The live index follows the current pose of resident moving fragments and drives
current residency decisions.

The persisted index describes the fragment payload revisions actually committed
to disk.

They cannot be blindly collapsed into one structure. If a moving fragment
updates the disk index before its payload is written, a crash can leave the
index pointing at a location the persisted payload does not occupy.

Eviction therefore commits in this order:

1. write the exact fragment payload snapshot;
2. update/write the matching persisted discovery index;
3. mark that exact revision clean;
4. only then allow storage eviction.

A fragment that changes while steps 1–2 are running stays dirty.

### Crash-window healing

DROP 0003 already identified the unavoidable two-file crash window: a fragment
payload may be atomically replaced and the process may die before the derived
index is replaced.

Full-store loading could recompute the index from every payload. Region-only
streaming cannot afford that on every startup.

When 0004.1 loads a payload through a stale discovery entry, it updates the live
index from the authoritative payload and heals the persisted index. If that
healing write fails, the fragment remains dirty so eviction or an explicit flush
retries rather than dropping an undiscoverable object.

### Sandbox host integration

Normal directory startup now loads the fragment index, not every fragment
payload.

A dedicated FragmentStreamRes and FragmentStreamTasks host layer:

- computes a storage-residency region window around the camera;
- discovers fragment ids through the spatial index;
- performs bounded asynchronous payload loads/saves;
- reconciles moving fragment spatial membership;
- removes clean unwanted payloads from DynamicFragments;
- leaves render and Avian physics residency as smaller independent layers.

The default storage radius is host policy and can be changed without changing
engine truth.

### Durability barriers

F5, F9 and process exit now treat fragment I/O the same way terrain flushing
already treats region I/O: outstanding fragment writes are finished before a
synchronous flush/reload/drop-residency barrier proceeds.

That prevents an old async write landing after F9 reloaded the world, shutdown
racing an unfinished fragment save, and F5 reporting durable state while a
required fragment write is still pending.

The runtime-only fragment smoke object remains excluded from persistence.

## 0004.2 — structural-demand region loading

**Status: complete**

DROP 0003 could name regions required to answer a structural question but had no
way to make those regions resident except waiting for ordinary camera streaming.

The generic region streamer now accepts a bounded external-demand set in
addition to the camera neighbourhood. Demanded regions:

- participate in the ordinary load scheduler rather than bypassing it;
- are deduplicated deterministically;
- are pinned against normal distance eviction while demand remains;
- still obey hard memory pressure and active-load limits;
- remain remembered when pressure temporarily withholds the load;
- become stale normally if the question releases demand before I/O returns.

The destruction host publishes the bounded union of regions named by pending
structural questions before the normal streaming update. A question at a region
boundary can therefore pull in the exact world data it needs without asking the
player to move the camera there.

The host exposes demanded/withheld counts in diagnostics. Tests pin far-region
loading, pin lifetime, deduplication, hard-budget withholding/recovery and stale
in-flight completion after demand release.

Formatter, full engine tests and workspace Clippy with warnings denied pass.

## 0004.3 — incremental fragment persistence

**Status: complete**

0004.1 already changed steady-state fragment saving from a whole-store rewrite
into per-fragment dirty revision writes. This pass closes the deletion and orphan
side of that contract.

### Authoritative deletion is index-first

A streamed world cannot infer deletion from absence in the resident
`FragmentStore`: most valid persisted fragments may intentionally be unloaded.

`delete_persisted_fragment` therefore requires an explicit authoritative
identity and commits in this order:

1. clone/remove the fragment from the authoritative discovery index;
2. atomically write that index;
3. only then remove the payload file.

A crash between steps 2 and 3 leaves an unreferenced payload. That is a harmless
orphan. Reversing the order could leave the durable index pointing at a missing
payload and make a valid world unloadable.

Ordinary storage eviction never calls authoritative deletion.

### Safe orphan pruning

`prune_fragment_orphans` removes payloads absent from an already-authoritative
index, but its precondition is deliberately strict: all fragment writes must be
quiesced and the index must already be durable.

F5/shutdown already establish the fragment-save barrier before synchronous
flush. Their flush path now commits the authoritative index and only then prunes
true orphans. This preserves the existing recoverable payload-first/index-second
crash window for new or moved fragments.

New persistence tests pin both streamed authoritative deletion and the simulated
crash window where the index commit succeeds but payload cleanup does not.

Validation passed:

- focused fragment persistence suite;
- formatter;
- workspace Clippy with warnings denied;
- sandbox/Bevy/Avian Clippy with warnings denied.

## 0004.4 — asynchronous fragment derived data

**Status: implementation complete; runtime acceptance in progress**

DROP 0003 bounded how many fragment meshes/bodies could be created per frame, but
one pathological fragment could still compile an expensive mesh or collider
synchronously on that frame.

The engine now exposes pure owned worker contracts:

- `FragmentMeshJobInput -> FragmentMeshJobResult`
- `FragmentCollisionJobInput -> FragmentCollisionJobResult`
- `FragmentGeometryFingerprint`

Mesh jobs own a fragment snapshot plus a cloned material registry and return
complete CPU `MeshData`. Collision jobs own a fragment snapshot and return the
canonical greedy `CollisionShape`. No Bevy, Avian or task-pool types enter an
engine crate.

### Geometry revision is separate from motion revision

The pre-existing fragment revision moves when physics updates pose, velocity or
sleep state because those values are persistent world state. It therefore cannot
be the stale key for local mesh/collision geometry: a falling fragment would
invalidate its worker job every physics tick.

Fragments now also expose a runtime geometry revision. Physics motion does not
move it. Future local-cell mutation/re-fracture must move it.

Tests prove that a mesh/collision result remains current after physics motion
while still carrying deterministic fragment identity.

### Sandbox worker queues

Fragment rendering now:

- dispatches at most four active CPU mesh jobs;
- stores completions in deterministic FragmentId order;
- rejects/cancels geometry-stale work;
- applies at most four GPU mesh uploads per frame;
- keeps budget-blocked fragments out until capacity increases.

Fragment physics now:

- dispatches at most eight active collision jobs;
- rejects/cancels geometry-stale work;
- combines a completed local collider with the fragment's current pose/velocity
  at body-creation time;
- applies at most eight Avian body creations per frame;
- retains the existing byte/body/box admission policy.

Thus moving while a job runs cannot rewind a fragment to the pose captured by
the worker input.

Formatter, focused destruction tests, workspace Clippy and sandbox Clippy with
warnings denied pass. Real sandbox destruction-smoke acceptance is the remaining
closeout check for this pass.
