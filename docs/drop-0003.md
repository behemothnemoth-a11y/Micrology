## 0003.1 — destruction measurement harness

DROP 0002's most expensive single discovery — that mesh cost per cell spans four
orders of magnitude — only turned up because the harness existed *before* the
optimisation it was going to judge. Destruction gets the same treatment first,
and for the same reason: nobody can say whether a connectivity search is cheap or
ruinous without a world to run it on.

```sh
cargo run --release -p engine_stress --bin structural            # measure and print
cargo run --release -p engine_stress --bin structural -- --check # compare to baseline
cargo run --release -p engine_stress --bin structural -- --write # regenerate it
```

Ten scenarios, each a structure, a set of anchored cells, and the damage it is
about to take:

| scenario | cells | anchors | volumes | regions | removed | expectation |
|---|---|---|---|---|---|---|
| `supported_column` | 416 | 256 | 3 | 1 | 12 | 0 detached |
| `cantilever` | 1,280 | 1,024 | 4 | 1 | 8 | 1 detached |
| `two_support_bridge` | 2,336 | 96 | 5 | 1 | 784 | 0 detached — one pier is enough |
| `cut_column` | 3,216 | 1,024 | 12 | 1 | 64 | 1 detached: the platform |
| `multi_island` | 624 | 16 | 12 | 1 | 16 | 4 detached |
| `volume_boundary_break` | 1,168 | 192 | 4 | 1 | 32 | 1 detached across the seam |
| `region_boundary_break` | 4,240 | 192 | 16 | **2** | 32 | 1 detached across the seam |
| `material_noise_structure` | 784 | 144 | 3 | 1 | 48 | 1 detached |
| `large_supported_structure` | 25,584 | 4,096 | 32 | 1 | 368 | 0 detached |
| `fragment_storm` | 10,240 | 4,096 | 16 | 1 | 1,024 | many detached |

The three that are easy to under-build, and what each is for:

- **`two_support_bridge`** is the *redundancy* case. Removing a support is not
  removing support, and a classifier that treats "lost a connection" as "lost
  its support" passes every other scenario here.
- **`large_supported_structure`** is the expensive **negative** case. Proving a
  25,584-cell structure is *still* supported means the search cannot stop early;
  a detachment never pays that cost. Any claim that connectivity is cheap has to
  answer to this one.
- **`region_boundary_break`** spans two residency regions, which is where
  "unknown is not empty" will eventually be tested for real.

### Anchors live beside the world, not inside the material

Anchors are carried as plain cell positions in the fixture rather than as a
property of `STONE`. That is the scope's rule made structural: **support is world
topology, not a material stat**, and the harness would quietly undermine it by
modelling anchoring any other way. World-side anchor storage arrives in 0003.3;
the scenarios will then hand their anchors to it rather than carrying them.

### What this pass can honestly measure

Most of `StructuralCounters` is **zero**. The engine that fills it in does not
exist yet, and the fields are present from the first commit for the reason
DROP 0002's were: a later pass should show up as a reviewable diff on a file that
was already being compared, not as a new file nobody compares against. A test
asserts they stay zero, so the pass that fills one in cannot do it by accident.

What *is* measured now is the thing everything else depends on — **the scenario
worlds themselves**, plus the static render geometry left after the damage. If a
structure's generation ever drifts, every downstream number drifts silently with
it; pinning the worlds first means a later connectivity change can be told apart
from a later fixture change.

### What it found immediately

`two_support_bridge` was cutting 1,152 cells where its pier only had 784: the
footing is wider than the pier it carries, and one box covering both half-missed.
The test that caught it asserts every damage cell lands on an occupied cell — a
scenario whose damage misses would measure nothing while looking like it measured
something, and would have reported a confident "0 detached" for entirely the
wrong reason.

The baseline is committed to `fixtures/stress/structural.json` and asserted in
`cargo test`. The geometry baseline is untouched: a destruction change and a
meshing change must never land in one diff and have to be told apart by eye.

## 0003.2 — batched, transactional world edits

Destruction removes hundreds or thousands of cells at once. Running the
single-cell path that many times is wrong in three separate ways, and only the
first is about speed:

1. **Redundant invalidation.** Carving a sphere out of one volume decides what to
   dirty once per cell. The dirty set deduplicates; the deciding does not.
2. **Repeated lookups.** Every write re-walks region → volume, when a thousand
   consecutive writes usually land in a handful of volumes.
3. **No result worth having.** A loop of `set` calls returns a count. What
   destruction needs is *which* cells stopped existing and which surviving cells
   are now next to a hole — and that cannot be reconstructed afterwards, because
   the edit itself destroys the information.

The third is why this pass comes before connectivity rather than after it.

### The batch is the path, not a path beside it

`World::fill_box` now goes through `apply`, so every bulk write in the engine
exercises the transaction rather than leaving it to destruction alone. The
invariant that keeps the two honest is a test: a batch must be **indistinguishable**
from the same edits applied one at a time — same cells, same dirty set, same
revision. If those ever diverge, every other test in the repo is testing one of
two engines.

Both stress baselines came back **byte-identical** after the `fill_box` rewrite,
which is the same check from the other direction: a change that was meant to be
invisible was provably invisible.

### `EditOutcome`

```rust
changed_cells          // repaints included
removed_cells          // occupied -> empty. ONLY these can detach anything
added_cells            // empty -> occupied
changed_volumes
dirtied_volumes        // changed, plus neighbours a boundary edit exposed
dirtied_regions
structural_candidates  // surviving occupied cells face-adjacent to a hole
unresolved_regions     // neighbours whose region is not resident
```

Removals, additions and repaints are reported **apart**. Adding or repainting a
cell cannot sever a connection, so `may_detach()` is false for them and
structural analysis never runs. That is not an optimisation to be verified later;
it is a statement about what detachment means.

### Unknown is not empty, from the very first step

A removed cell's neighbour may lie in a region that is not resident. The world
cannot tell that from empty space by looking at cells — both answer `None` — so
the batch checks **region residency** instead and reports what it could not see.

This matters more than it looks. If an unloaded neighbour were silently read as
empty there would be no candidate root, so no analysis would run at all, and a
structure supported from across the seam would be invisible to the pipeline
rather than merely misclassified by it. The rule has to start here, not at the
classifier.

The distinction is between *no record* and *an empty record*: a `World` holds a
region record for everything the streamer has decided about, loaded-empty
included. No record means not yet decided, which means unknown.

### Candidate roots, now measured

The structural baseline moved in exactly one field, `candidate_roots`:

| scenario | removed | roots |
|---|---|---|
| `supported_column` | 12 | 4 |
| `cantilever` | 8 | 16 |
| `two_support_bridge` | 784 | 32 |
| `cut_column` | 64 | 32 |
| `multi_island` | 16 | 32 |
| `volume_boundary_break` | 32 | 32 |
| `region_boundary_break` | 32 | 32 |
| `material_noise_structure` | 48 | 32 |
| `large_supported_structure` | 368 | 32 |
| `fragment_storm` | 1,024 | **2,048** |

`fragment_storm`'s 2,048 is the number to keep in view: 256 stubs, each severed
at its root, each leaving the stub above and the plate below as roots. Those 2,048
starting points will resolve into 256 components and one supported plate, and
whether that is cheap or ruinous is exactly what 0003.5 has to answer.

Note that `two_support_bridge` removes 784 cells and `fragment_storm` 1,024, yet
the bridge yields 32 roots and the storm 2,048. Roots scale with the *surface* of
the damage, not its volume — which is the first measured hint that connectivity
cost will not track how much was destroyed.

### Sphere carving

`carve_sphere` is here rather than in the sandbox because determinism is an
engine property. Distances are compared **squared, in integers**: a carve must
land on exactly the same cells on every machine, and a float comparison at the
rim is precisely where that would stop being true.
